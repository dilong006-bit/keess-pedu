## 2. ★ 반드시 함께 정정할 것 — 이전 판단이 뒤집혔다

`relead-r3`의 요청 원문은 `12/17(수)~18(금)`이었다.
README §50과 후속 항목 13번에 아래와 같이 기록돼 있다.

> "틀린 것은 **요일 라벨 `(수)` 하나뿐**이고(2026-12-17=목) 날짜 17~18은 2일로 과정 길이와 정합한다."

**확정본은 `12/16~17`이고, 이는 수요일 ~ 목요일이다.**

| 원문 요소 | 당시 판단 | **실제** |
| --- | --- | --- |
| 시작 요일 `(수)` | 틀렸다 | **맞았다** (12/16 = 수) |
| 날짜 `17~18` | 맞았다 | **틀렸다** (실제 16~17) |
| 종료 요일 `(금)` | 틀렸다 | 틀렸다 (12/17 = 목) |

**당시 판단이 정확히 반대였다.** 원문에서 신뢰할 수 있었던 것은 **요일**이었고 날짜가 어긋나 있었다.

> **설계 자체는 여전히 유효하다.** 요일을 저장하지 않고 `start`에서 파생하므로,
> 확정 날짜만 넣으면 화면에는 `12.16(수) ~ 17(목)`으로 정확히 출력된다.
> 다만 **"원문의 요일이 틀렸다"는 당시의 근거는 사실이 아니었으므로 문서에서 정정한다.**

이 정정을 README에 반영하지 않으면, 다음 사람이 잘못된 전제로 원문을 해석한다.

## 3. ★ 적용 시 주의 — 세 건을 한 번에 반영한다

현행에서 **`relead-r3`(12.17~18)와 `onpow-r2`(12.16~17)는 12/17에 겹쳐 있다.**

| 순서 | 상태 |
| --- | --- |
| `relead-r3`만 먼저 12.16~17로 변경 | `onpow-r2`(아직 12.16~17)와 **완전히 동일한 일자**가 된다 |
| `onpow-r2`만 먼저 12.28~29로 변경 | 문제 없음 |
| **세 건 동시 반영** | 겹침 **0건** — 권장 |

배열 데이터라 런타임 오류는 나지 않지만, **중간 커밋을 남기지 말고 한 번에** 반영한다.
확정 후 20회차 전체에 **완전 동일 일자 조합은 0건**이다.

## 5. 변경 명세

### 5-1. `lib/kium/sessions.ts` — 데이터 3건

`start` · `end` 값만 교체한다. 같은 줄의 `id` · `courseId` · `displayMonth` · `status`,
그리고 **배열 순서**는 한 글자도 바꾸지 않는다.

```ts
{ id: 'cs-r2',     courseId: 'kium-19', displayMonth: 11, start: '2026-11-20', end: '2026-11-20', status: 'confirmed' },
{ id: 'relead-r3', courseId: 'kium-04', displayMonth: 12, start: '2026-12-16', end: '2026-12-17', status: 'recruiting' },
{ id: 'onpow-r2',  courseId: 'kium-03', displayMonth: 12, start: '2026-12-28', end: '2026-12-29', status: 'recruiting' },
```

파일 상단 주석의 `relead-r3` 관련 문단을 아래로 **교체**한다.

```
 *   ★ 일자 확정 개정 3건(F24) — cs-r2 · relead-r3 · onpow-r2.
 *     근거는 HRD솔루션팀 확정 통보(Google Sheets N열 교육시작일 · O열 교육종료일)다.
 *     relead-r3의 요청 원문 `12/17(수)~18(금)`에 대해 이전에는
 *     "요일 라벨만 틀렸고 날짜 17~18은 맞다"고 판단했으나, 확정본은 12/16~17(수~목)이다.
 *     즉 원문에서 신뢰할 수 있었던 쪽은 요일이었고 날짜가 어긋나 있었다.
 *     요일을 저장하지 않고 start에서 파생하는 설계 자체는 유효하다 —
 *     확정 날짜만 넣으면 화면에 12.16(수) ~ 17(목)으로 정확히 출력된다.
```
