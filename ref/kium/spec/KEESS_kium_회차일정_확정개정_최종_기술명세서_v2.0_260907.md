## 1. 무엇을 왜 바꾸는가

### 1-1. 대상

`agent-r3` — AI활용 업무효율화: Agent 과정 3회차 · `2026-11-30(월) ~ 2026-12-01(화)`.
20회차 중 **월 경계를 넘는 회차는 이 한 건뿐이다.** 따라서 본 건은 **정책 1건으로 종결**되며 데이터 모델 변경이 없다.

### 1-2. 현행이 가장 나쁜 조합이다

기간 필터는 `displayMonth`로 걸리는데 **정렬·과거 판정은 `start`** 기준이다.
`displayMonth: 12` + `start: 11-30` 조합의 결과는 이렇다.

| 사용자 행동 | 현행 결과 |
| --- | --- |
| **12월** 필터 | 「12월 8개 회차」 그룹의 **첫 줄이 `11.30`** — 12월을 골랐는데 11월 날짜가 맨 위에 나온다 |
| **11월** 필터 | **이 회차가 사라진다** — 11월 30일에 시작하는데도 |

12월에서는 이질적으로 튀고, 11월에서는 아예 없어진다. **양쪽 다 손해다.**
현행 검증 스크립트의 `U5` 단언(`12월 그룹 = 11.30 · 12.7 · …`)이 이 결함을 그대로 고정하고 있다.

### 1-3. 확정 근거 — 11월

| # | 근거 |
| --- | --- |
| 1 | **회차 선택의 기준점은 시작일이다.** 신청 마감·개강 확정·참석 준비가 전부 시작일 기준으로 움직인다. 기간 필터를 쓰는 질문도 *"11월에 시간이 되는데 뭐가 있나"* 이고, 이 교육에 참여하려면 **11월 30일에 시간을 비워야 한다** |
| 2 | **정렬과 필터가 일치한다.** 11월 그룹의 자연스러운 마지막(`… 11.20 · 11.30`)이 되고, 12월 그룹은 `12.7`부터 깨끗하게 시작한다 |
| 3 | **화면 표기와 맞는다.** 카드에 `11.30(월) ~ 12.1(화)`로 이미 11월이 앞에 나온다 |
| 4 | **12월 검색자의 손실이 작다.** 12월만 가능한 사람은 11/30 시작 교육에 참석할 수 없다. 종료일 `~ 12.1(화)`가 이미 화면에 있으므로 별도 표시도 필요 없다 |

### 1-4. 채택하지 않은 대안

| 대안 | 판정 |
| --- | --- |
| **12월 유지** | **기각.** §1-2 |
| **양쪽 노출**(`displayMonth` 배열화) | **기각.** 기간 칩 카운트 합이 전체 회차 수와 어긋난다(6+7+8 = **21** vs 20). 숫자가 안 맞는 필터는 그 자체로 신뢰를 잃는다. 한 건 때문에 데이터 모델을 바꿀 일이 아니다. 원천 시트의 `11월, 12월` 표기는 **"두 달에 걸친다"는 사실 기술**로 읽는다(다른 행은 전부 단일값) |
| 「12월 종료」 부가 배지 | **기각.** 날짜(`~ 12.1(화)`)가 이미 그 사실을 말한다. 한 건을 위한 신규 UI 요소는 과잉이다 |

## 3. 변경 명세

### 3-1. `lib/kium/sessions.ts` — 값 1개

```ts
{ id: 'agent-r3',  courseId: 'kium-09', displayMonth: 11, start: '2026-11-30', end: '2026-12-01', status: 'closing' },
```

**`displayMonth`만 `12` → `11`.**
`id` · `courseId` · `start` · `end` · `status` · **배열 순서**는 한 글자도 바꾸지 않는다.

### 3-2. `sessions.ts` 상단 주석 — 문단 1개 추가

기존 `★ 일정 확정 개정 3건(F24)` 문단 **바로 아래에 덧붙인다**(기존 서술 삭제 금지).

```
 *   ★ 월 경계 회차의 귀속(F25) — agent-r3(11/30~12/1)를 displayMonth 11로 둔다.
 *     기간 필터는 displayMonth로 걸리는데 정렬·과거 판정은 start 기준이다.
 *     12로 두면 「12월」 그룹의 첫 줄에 11.30이 튀고, 11월 필터에서는
 *     11/30 시작인데도 사라진다 — 양쪽 다 손해였다.
 *     회차 선택의 기준점은 시작일이다(신청 마감·개강 확정·참석 준비가 전부 시작일 기준).
 *     양쪽 노출(displayMonth 배열화)은 기간 칩 카운트 합이 전체 회차 수와
 *     어긋나므로(21 vs 20) 채택하지 않는다. 월 경계 회차는 20건 중 이 1건뿐이라
 *     데이터 모델을 바꿀 일이 아니다.
```

### 4-3. ★ 모집 상태 칩 — 12월에서 「마감임박」이 사라진다

F22(0건 칩 미노출) 규칙의 결과다.

| 기간 필터 | 노출 칩 | 개수 |
| --- | --- | --- |
| 전체 | `전체 20 / 모집중 8 / 개강확정 6 / 마감임박 5 / 마감 1` | 5 |
| 10월 | `전체 6 / 모집중 2 / 개강확정 1 / 마감임박 2 / 마감 1` | 5 |
| **11월** | **`전체 7 / 모집중 2 / 개강확정 2 / 마감임박 3`** | **4** |
| **12월** | **`전체 7 / 모집중 4 / 개강확정 3`** | **3** ← 마감임박까지 사라짐 |

**이는 정상 동작이며 오히려 검증 자산이다.**
`agent-r3`(`closing`)가 11월로 옮겨가 12월의 `closing`이 0건이 되었다.
F22가 의도한 *"0건 칩은 선택지가 아니라 잡음"* 이 **실제 데이터에서 두 단계(4개 → 3개)로 발현**되는 케이스가 새로 생겼다.

**시드 커버리지에 대한 판단 — 보정하지 않는다.**

| 근거 |
| --- |
| `status`는 검토용 시드이며 **오픈 전 실제 회신값으로 전건 교체**될 값이다. 커버리지를 맞추려 시드를 계속 조정하는 것은 목적이 전도된 것이다 |
| **4상태 전부 확인은 `10월` 필터 하나로 가능**하다 — 시드 설계의 원래 의도 그대로다 |
| 12월의 칩 3개 상태는 **F22 동작 자체를 검증할 케이스**를 새로 만들어 준다 |
