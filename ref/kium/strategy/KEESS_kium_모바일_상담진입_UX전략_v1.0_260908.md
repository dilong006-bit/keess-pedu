# `/kium` 모바일 상담 진입 UX 전략 v1.0

- 대상: `/kium#courses` 「상담하기」 탭 이후의 도입문의 폼 진입 경로
- 기준 커밋: `43e22de`
- 근거: 실기기 스크린샷 2매(현재 / 제안) + 코드 실사

---

## 1. 사용자가 말한 것

| 관찰 | 사용자 표현 |
| --- | --- |
| 컨텍스트 상실 | "어떤 과정에 대해 신청하고 있는지 알기 어렵다" |
| 포커스 상실 | "어떤 항목을 입력하기 위해 키보드가 활성화 되어 있는지는 더더욱 알기 어렵다" |
| 원하는 상태 | 폼 입력 필드가 화면에 보이고, 포커스 위치를 알 수 있는 상태 |

**키보드가 뜨는 것 자체를 문제 삼지 않았습니다.** 키보드가 떠 있는데 그 대상이 보이지 않는 것이 문제입니다. 따라서 자동 포커스를 없애는 것이 아니라, 포커스 대상을 보이게 하는 것이 해법입니다.

---

## 2. 원인 (추정 아님, 코드 확인)

### 원인 1. 스크롤 앵커가 소개 카피를 가리킨다

```
openBridge.ts:112   document.getElementById('inq').scrollIntoView({ block:'start' })
```

`#inq` 섹션의 첫 자식은 폼이 아니라 소개 블록입니다.

```
<section id="inq">
  <div class="inq-grid">
    <div class="inq-side">   ← min-height:340px · padding:40px · 보라 그라디언트
    <div class="form">       ← 실제 입력 필드
```

`.inq-grid`는 880px 이하에서 1열이 되므로(`home.css:209`), 모바일에서 앵커 위치는 **340px 넘는 소개 블록의 최상단**입니다. 스크린샷의 보라 박스가 정확히 이것입니다.

### 원인 2. 컨텍스트 배너가 앵커보다 위에 있다

```
<div class="kium-cta-band">
  <KiumApplySummary />     ← 과정명·회차를 보여 주는 배너
  <HomeInquiry>            ← 이 안에 #inq
```

`#inq`로 스크롤하면 배너는 **화면 위로 밀려납니다.** 배너는 정상 동작하고 있는데 구조상 볼 수 없습니다. 스크린샷에 배너가 없는 이유입니다.

### 원인 3. 자동 포커스가 화면을 움직이지 않는다

```
openBridge.ts:116   setTimeout(() => document.getElementById('f-company')?.focus({ preventScroll:true }), 480)
```

`preventScroll:true`는 데스크톱에서 옳은 선택입니다. 2열 레이아웃이라 소개와 폼이 함께 보이고, 화면이 두 번 흔들릴 이유가 없습니다.

모바일에서는 정반대로 작동합니다.

- 뷰포트가 좁아 소개 블록만으로 화면이 찬다
- 포커스가 걸리면 키보드가 하단 약 45퍼센트를 덮는다
- `preventScroll:true`이므로 **보정이 일어나지 않는다**

결과: 포커스된 입력은 키보드 뒤 또는 화면 밖입니다.

### 원인 4. 앵커 보정값이 없다

`scroll-margin-top` 선언이 **전 CSS에 0건**입니다. `.nav`는 `position:fixed`, `.subnav`는 `position:sticky`이므로 앵커 스크롤 시 상단이 헤더에 가립니다. 스크린샷에서 제목이 탭바에 잘려 있는 것이 이 결과입니다.

### 원인 5. 일부 경로는 배너 자체가 뜨지 않는다

| 경로 | 진입 | 배너 |
| --- | --- | --- |
| 회차 카드 「상담하기」 | `KIUM_OPEN_SELECT_EVENT` 발생 | 있음 |
| 과정 패널 「상담 신청」 (`KiumCoursePanel.tsx:229`) | 프리필만 발생 | **없음** |

두 번째 경로는 컨텍스트가 `문의 내용` textarea 안에만 존재합니다. 폼 하단이라 모바일에서는 사실상 보이지 않습니다.

## 3. 전략 원칙

### 원칙 1. 앵커는 "지금 무엇을 해야 하는가"를 가리킨다

「상담하기」를 누른 사용자에게 필요한 것은 소개 문구가 아니라 **입력 필드**입니다. 소개는 이미 읽고 결심한 사람에게는 장애물입니다.

- 앵커 대상: `#inq` → **폼 컨테이너**
- 모바일에서 소개 블록은 폼 **아래로** 보낸다 (삭제하지 않는다)

### 원칙 2. 컨텍스트는 스크롤을 따라다닌다

무엇을 신청 중인지는 폼을 채우는 내내 유효한 정보입니다. 한 번 지나가면 사라지는 위치에 두지 않습니다.

- 배너를 앵커 **안쪽**으로 들어오게 한다
- 모바일에서 배너를 sticky로 고정한다
- 배너가 뜨지 않는 경로를 없앤다

### 원칙 3. 키보드를 레이아웃의 일부로 계산한다

브라우저의 기본 스크롤 보정은 sticky 요소의 존재를 모르고, `preventScroll:true`가 걸려 있으면 아예 동작하지 않습니다.

- `visualViewport`로 **실제 가시 높이**를 읽는다
- 키보드 등장 이후 포커스 대상이 가려지면 보정한다

### 원칙 4. 데스크톱은 바꾸지 않는다

현행 데스크톱 동작은 옳습니다. 모든 변경은 모바일 조건에서만 발현되거나 시각 중립이어야 합니다.

### 원칙 5. 공유 폼을 건드리지 않는다

`HomeInquiry`는 5개 페이지가 공유합니다. 필드·검증·동의 구조를 바꾸지 않는다는 기존 원칙을 유지하고, 변경은 `/kium` 스코프(`.kium-cta-band`)로 한정합니다.

## 5. 채택하지 않은 대안

| 대안 | 판정 |
| --- | --- |
| 모바일에서 자동 포커스 제거 | **기각.** 사용자는 키보드를 부정하지 않았습니다. 포커스를 없애면 탭을 한 번 더 요구하게 되고, 어느 항목부터 시작할지 신호가 사라집니다 |
| 소개 블록을 모바일에서 숨김 | **기각.** 신뢰 요소(회신 기준·실적)를 잃습니다. 순서만 바꿉니다 |
| 폼을 바텀시트·전용 페이지로 분리 | **기각.** 공유 폼 구조를 깨고 회귀 범위가 5개 페이지로 번집니다. 본 건은 진입 경험 문제이지 폼 구조 문제가 아닙니다 |
| `HomeInquiry`에 모바일 전용 분기 추가 | **기각.** 공유 컴포넌트 오염. `/kium` 스코프 CSS와 호출부에서 해결 가능합니다 |
| 키보드 높이를 CSS `env(keyboard-inset-height)`로 처리 | **기각.** 지원 범위가 좁습니다. `visualViewport`가 사실상 표준입니다 |
