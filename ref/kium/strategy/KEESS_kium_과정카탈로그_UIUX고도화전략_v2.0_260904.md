## 1. '정부지원 환급' 칩 — 제거가 아니라 승격

### 1-1. 현황

```tsx
// components/kium/KiumCourseCard.tsx:88
{!isOpen && <span className="kium-badge gov">정부지원 환급</span>}
```

전체 보기에서 **19장 카드 전부**에 동일 배지가 붙는다.

### 1-2. 왜 지워야 하는가

| 관점 | 문제 |
| --- | --- |
| 정보량 | 19개 중 19개에 붙은 라벨의 변별력은 **0**이다. "이 카드가 저 카드와 무엇이 다른가"에 아무 답도 하지 않는다 |
| 시각 | 카드 메타 행(대상 · 시간/일수 · 배지)에서 가장 진한 색(`--gov #F4B83A`)을 차지해, 정작 카드마다 다른 정보인 **대상·시간**보다 먼저 읽힌다 |
| 접근성 | 스크린리더가 카탈로그를 훑을 때 "정부지원 환급"을 **19번 반복 낭독**한다 |
| 모바일 | 1열 배치에서 메타 행이 2줄로 접히는 주된 원인 |

### 1-3. 지우기만 하면 안 되는 이유

'정부지원 환급'은 이 사업의 **최대 소구점**이다. 카드에서 빼되 **한 번은 반드시 말해야 한다.** 반복이 문제였지 메시지가 문제인 게 아니다.

### 1-4. 확정안

| 항목 | 내용 |
| --- | --- |
| 카드 | `.kium-badge.gov` **렌더 제거** (전체 보기·공개교육 보기 양쪽) |
| 승격 위치 | 과정안내 탭 **카탈로그 인트로 1줄** — 공개교육 보기의 `.kium-modehead-s`("1명부터 신청 가능 · 정부지원 환급")와 **대칭**되는 자리 |
| 전체 보기 문구 | `19개 과정 전체가 정부지원 환급 대상입니다` — 카운트는 데이터 파생 |
| 유지 | **`공개교육` 칩은 그대로 둔다.** 9/19에만 붙어 변별력이 있다 |
| 상세 패널 | `KiumCoursePanel`의 환급 관련 표기는 무변경 — 개별 과정을 결정하는 자리에서는 필요한 정보다 |

### 1-5. 확보되는 공간

메타 행이 `대상 · 시간/일수` 두 항목으로 정리된다. 여기에 **공개교육 9과정의 회차 요약**(`🗓 10~12월 3개 회차`)을 넣으면, 카드에서 바로 "언제 열리는지"를 알 수 있어 배지 하나를 뺀 자리에 **실제 정보**가 들어간다.

## 2. 썸네일 실사화 — 19장 전건

### 2-1. 현황과 문제

| 세트 | 대상 | 상태 |
| --- | --- | --- |
| `data.ts` `thumbSrc` | kium-01·02·03 | `*.sample.jpg` 3장 — **임시 샘플** |
| `openThumbs.ts` | kium-03·04·09·10·11·12·13·14·19 | 공개교육 보기 전용 9장 |
| 나머지 | 10과정 | 텍스트 모드(퍼플 그라디언트) |

첨부 화면에서 그대로 드러난다. **첫 행 3장은 실사, 둘째 행 '승진자' 3장은 퍼플 블록**이다. 사용자에게 이 혼재는 "스타일 선택"이 아니라 **"아직 안 만든 것"**으로 읽힌다. 카탈로그의 신뢰도가 여기서 깎인다.

### 2-2. ★ 먼저 해결해야 할 정책 충돌

두 세트의 인물 정책이 **서로 어긋나 있다.**

| 세트 | 인물 정책 | 근거 |
| --- | --- | --- |
| `open/` 9장 | **인물 얼굴 식별 컷 배제** — 후보 4건 반려 후 재선정 | `public/images/kium/open/README.md` |
| `*.sample.jpg` 3장 | **얼굴이 명확히 식별되는 인물 컷** | 첨부 화면 육안 확인 |

19장을 한 화면에 놓으면 이 불일치가 즉시 보인다. **정책을 먼저 하나로 정하고 19장을 선정해야 한다.**

| 안 | 내용 | 평가 |
| --- | --- | --- |
| **A (권장)** | **인물 얼굴 식별 컷 배제** — `open/` 기존 원칙으로 통일. 공간·도구·손·화면 중심 | 초상권 리스크 0. 톤 통일이 쉽고, 국내 B2B 사이트에서 서구권 인물 사진은 이질감을 준다. sample 3장은 교체 |
| B | 인물 컷 허용 (Unsplash License는 상업적 사용 가능) | 카탈로그가 따뜻해지지만 **모델 릴리스는 Unsplash가 보장하지 않는다**. 교육 서비스 맥락에서 특정 인물이 수강생으로 오인될 여지 |

> Unsplash License는 **저작권**만 다룬다. 사진 속 인물의 **초상권·퍼블리시티권은 별개**이며, 광고성 맥락에서는 촬영자가 아니라 게시자가 책임진다. A안을 권장하는 실질적 이유가 여기에 있다.

### 2-3. 확정 규격

기존 `open/README.md` 규격을 19장으로 승계한다.

| 항목 | 값 |
| --- | --- |
| 비율·해상도 | **4:3 · 1200×900** (코드 쪽 크롭 로직 없음 — 제작 단계에서 크롭 완료) |
| 포맷 | JPG. **WebP 전환 검토**(§2-6) |
| 용량 | **장당 300KB 이내** |
| 경로 | `public/images/kium/` — `kium-01.jpg` ~ `kium-19.jpg` (`.sample` 접미 제거) |
| 금지 | 이미지 위 텍스트 합성 · 워터마크 · 로고 · 비율 왜곡 · 원격 URL 핫링크 |
| 라이선스 | Unsplash License만. **`plus.unsplash.com`(유료 Unsplash+) 제외** |
| 기록 | `public/images/kium/README.md`에 19건 전건 출처·촬영자·용량 표 (기존 `open/README.md` 형식 승계) |

### 2-4. 카테고리별 톤 가이드

카테고리는 이미 카드에 **컬러 도트**로 표시된다. 사진 톤이 그 그룹핑을 거스르지 않아야 한다.

| 카테고리 | 과정 | 소재 방향 | 피할 것 |
| --- | --- | --- | --- |
| 신입·온보딩 (3) | kium-01·02·03 | 밝은 오피스 공간, 빈 데스크, 창가 자연광 | 정장 단체사진, 악수 클리셰 |
| 승진자 (3) | kium-05·06·07 | 회의실 테이블, 노트·펜, 계단·복도 | 사다리·화살표 상승 은유 |
| 리더십·관리자 (3) | kium-04·08·18 | 원형 테이블, 화이트보드, 창밖 도시 | 권위적 임원실, 지휘 제스처 |
| AI활용 (3) | kium-09·10·11 | 노트북 화면, 코드·대시보드, 데이터 시각화 | 로봇·안드로이드, 파란 네온 회로 |
| 비즈니스 역량 (3) | kium-12·13·14 | 마이크, 발표 좌석, 문서·필기 | 무대 조명 과다 |
| 커뮤니케이션·조직활성화 (3) | kium-15·16·17 | 마주 앉은 의자, 커피, 포스트잇 | 이모지·하트 소품 |
| CS·민원응대 (1) | kium-19 | 헤드셋, 상담 데스크 | 콜센터 밀집 부스 |

**공통**: 채도 낮은 중성 톤. 카드 그리드에서 한 장만 튀면 그 장이 아니라 **카탈로그 전체가 산만해 보인다.**

### 2-5. 데이터 구조 — `openThumbs.ts` 폐지 후 일원화

현재 `openThumbs.ts`는 "공개교육 탭만 이미지, 과정안내 탭은 텍스트"라는 조건 때문에 분리됐다. **19장 전건 실사화로 그 조건이 사라진다.**

| 항목 | 확정 |
| --- | --- |
| 단일 소스 | `lib/kium/data.ts`의 `thumbSrc` **19건 전건 설정** |
| `lib/kium/openThumbs.ts` | **폐지**. `KiumCourseGrid`의 `thumbs` prop과 주입 코드도 함께 제거 |
| 기존 `open/` 9장 | `public/images/kium/`로 **이동·개명**(`kium-09.jpg` 등). 이미 규격·정책을 충족하므로 재선정 불필요 |
| 신규 제작 | **10장** — kium-01·02·05·06·07·08·15·16·17·18 (kium-03·04는 `open/`에서 승계) |

> **같은 과정이 탭에 따라 다른 사진이면 안 된다.** 사용자는 "다른 과정인가?"로 읽는다. 1과정 = 1장 원칙을 코드 구조로 강제한다.

### 2-6. 성능 — 19장이 들어오면 무게가 달라진다

`next.config.mjs`에 `images.unoptimized: true`가 설정돼 있어 **Next.js 이미지 최적화가 없다.** 원본이 그대로 나간다.

| 항목 | 명세 |
| --- | --- |
| 총량 | 19장 × 300KB = **최대 5.7MB**. 실측 목표 **3.5MB 이하** |
| 지연 로딩 | `components/common/Img.tsx`가 이미 `loading="lazy"` + `decoding="async"` 기본 — **추가 작업 없음** |
| eager | 첫 행 **3장만** `eager` 지정. 나머지는 lazy 유지 |
| CLS 방지 | `.kium-thumb`가 `aspect-ratio:4/3`을 이미 갖고 있어 레이아웃 시프트 없음 — **유지 확인만** |
| WebP | JPG 대비 30~40% 감소. `<img src>` 단일 경로이므로 **파일만 `.webp`로 교체하면 코드 수정 0**. 지원율 문제 없음 → **WebP 권장** |
| 폴백 | `Img`의 `onError` → `display:none` → `.kium-thumb` 그라디언트 배경이 드러남. **텍스트 모드는 폴백 표면으로 영구 존치** |

### 2-7. 접근성 — `alt`를 비워야 한다

```tsx
// 현행 KiumThumb.tsx
<Img className="kium-thumb-img" src={thumbSrc} alt={title} />
```

이미지 모드에서는 카드 본문에 `.kium-card-title`이 **실제 텍스트로 렌더된다.** 지금 구조는 버튼의 접근 가능한 이름에 과정명이 **두 번** 들어간다.

**확정**: 썸네일은 장식이므로 `alt=""`로 두고, 과정명은 본문 텍스트가 담당한다. `Img`의 `alt` 기본값이 이미 `''`이므로 **`alt` prop만 제거**하면 된다.

## 3. 공개교육 안내 문구 리라이팅

### 3-1. 현행 진단

> 일부 과정은 공개교육으로 1명부터 신청하실 수 있습니다. **공개교육 일정 보기 →**

| 문제 | 설명 |
| --- | --- |
| **첫 단어가 제약** | "일부 과정은"으로 연다. 좋은 소식을 한계로 시작하면 읽는 사람은 "내 관심 과정은 아니겠지"로 넘긴다 |
| 수동 설명체 | "~하실 수 있습니다"는 제도 안내문의 문형이다. 카탈로그 상단은 **말 거는 자리**다 |
| 대상 부재 | 이 문장이 **누구에게** 좋은 소식인지가 없다. 읽는 사람이 자기 상황과 연결할 고리가 없다 |
| 사실은 정확 | 정보 오류는 없다. **고쳐야 할 것은 정확성이 아니라 순서다** |

### 3-3. 평가와 권장

| C | 사업 구조를 정확히 전달. 오해 여지 최소 | 회사 관점 문장이다. 사용자가 아니라 **운영자가 하고 싶은 말**에 가깝다 |

**주신 예시 3개 평가**

| "1명부터 신청 가능한 공개교육 과정도 준비되어 있습니다." | 정확하지만 여전히 **고지문**이다. "준비되어 있습니다"는 행동을 부르지 않는다 |
| "혼자서도 부담 없이 신청할 수 있는 공개교육 과정을 확인해보세요." | **가장 좋다.** '혼자서도', '부담 없이'가 사용자 언어다. 다만 이 페이지의 실제 신청 주체는 기업이라 **'혼자'가 개인 결제로 오해될 수 있다**(FAQ 2번과 충돌) |
| "기업 단체교육뿐 아니라, 1명부터 신청 가능한 공개교육도 운영합니다." | C안과 동일 구조. 정확하나 회사 관점 |

> **'혼자'라는 단어는 쓰지 않는다.** 기존 FAQ가 "개인 자격의 신청·결제는 지원되지 않습니다"라고 명시하고 있어, 같은 페이지 안에서 충돌한다. A안의 **"인원이 적어도"**는 같은 감정을 전달하면서 이 함정을 피한다.

## 4. 기간 필터 숫자 — ★ 단순한 UI 결함이 아니다

### 4-1. 문제의 정확한 성격

```tsx
// KiumCoursesTab.tsx:388
{m}월 <span className="cnt">{monthCount(m)}</span>   // → "10월 6"
```

지적하신 대로 `6`·`7`의 의미를 알 수 없다. **그런데 문제는 '모호함'이 아니라 '오독'이다.**

> **필터 행의 라벨이 「기간」이다.** 기간 옆에 붙은 숫자는 **일수(日數)로 읽힌다.**
> `10월 6` → "10월에 6일짜리 과정" 또는 "10월 6일"

실제 값은 **회차 수**다. 의미를 모르는 것보다 **틀리게 아는 것이 나쁘다.** 이 축은 다른 축과 같은 문제가 아니다.

### 4-2. 축마다 카운트의 성격이 다르다

| 축 | 칩 예시 | 오독 위험 | 카운트의 효용 |
| --- | --- | --- | --- |
| 분야 | `AI활용 3` | 낮음 — 분야명 옆 숫자는 자연히 '개수'로 읽힌다 | **높음** — 0건 카테고리 회피 |
| 모집 상태 | `모집중 12` | 낮음 — 동일 | **높음** — 개강확정이 몇 건인지가 결정에 직결 |
| **기간** | `10월 6` | **높음** — 날짜·일수로 읽힌다 | 중간 — 선택지가 3개뿐이라 어차피 다 본다 |

**일괄 처리하면 안 된다.** 모호성이 실제로 발생하는 축에만 단위를 붙인다. 세 축에 전부 단위를 붙이면 칩 폭이 커져 모바일에서 필터 바가 3줄이 된다.

### 4-3. 확정안

| 칩 | 현행 | 개선 |
| --- | --- | --- |
| 기간 · 전체 | `전체 19` | **`전체 19회차`** |
| 기간 · 월 | `10월 6` | **`10월 6회차`** |
| 분야 | `AI활용 3` | **유지** |
| 모집 상태 | `모집중 12` | **유지** |

**접근성 보강** — 시각 라벨과 무관하게 전 칩에 완전한 접근명을 준다.

```tsx
aria-label={`${m}월, ${monthCount(m)}개 회차`}
```

**반응형 확인** — 기간 칩은 4개(`전체`/`10월`/`11월`/`12월`)뿐이다. `6회차` 3글자를 더해도 375px에서 2줄 이내에 들어간다. 분야 칩 8개에 단위를 붙이지 않는 이유가 여기에도 있다.

### 4-4. 덤 — 이미 있는 자산을 살린다

`KiumCoursesTab.tsx:331`에 `aria-live` 결과 문구가 **`.kium-sr`(화면 낭독 전용)로 숨겨져** 있다.

```tsx
<p className="kium-sr" aria-live="polite">{live}</p>
```

스크린리더 사용자만 필터 결과를 듣고, **눈으로 보는 사용자는 못 본다.** 이 문구를 필터 바 하단에 시각적으로도 노출하면 칩 숫자에 대한 의존이 줄어든다.

> `10월 · 개강확정 · 6개 회차`

## 5. 캘린더 보기 — 보류(P2), 대안 2종

### 5-1. 데이터로 먼저 판단한다

| 지표 | 값 |
| --- | --- |
| 기간 | 10/1 ~ 12/31 = **92일** |
| 개강 회차 | **19건** |
| 개강일이 있는 날 | 19일 = **20.6%** |
| 월간 그리드 빈 칸 | **약 79%** |
| 2일 과정 비중 | 11/19 = **58%** — 캘린더에서 연속 2칸 span 필요 |

**캘린더는 밀도가 높을수록 이기는 포맷이다.** 하루 여러 건이 겹치는 일정에서 진가를 발휘하는데, 이 데이터는 월 6~7건이다. 79%가 빈 칸인 그리드는 정보를 주는 대신 **화면만 크게 차지한다.**

### 5-2. 반응형이 결정적이다

375px에서 7열 그리드 → 열당 **약 47px**. 날짜 숫자와 점 하나가 한계다. 과정명은 절대 못 들어간다. 결국 **"점을 탭해서 상세를 여는" 2단계**가 되는데, 지금 리스트 뷰는 **탭 없이 바로 다 보인다.** 모바일에서 캘린더는 명백한 퇴보다.

### 5-3. 그래도 캘린더를 원하는 진짜 이유

사용자가 캘린더를 찾는 순간의 질문은 **"이 날짜가 내 일정과 겹치나?"**이다. 그 질문의 정답은 **사이트 안의 캘린더가 아니라 사용자 본인의 캘린더**에 있다.

### 5-4. 대안 2종

**대안 A — 회차 카드에 「캘린더에 추가」 (권장 · P1)**

| 항목 | 내용 |
| --- | --- |
| 동작 | 회차 카드에서 `.ics` 파일 1건 다운로드 → Outlook·Google·Apple 캘린더에 그대로 등록 |
| 내용 | 과정명 · 일자(종일 일정) · 장소 · `/kium#open?course=&round=` 링크 |
| 왜 이기는가 | "겹치나?"라는 질문에 **사용자의 실제 일정으로** 답한다. 사이트 캘린더는 그 답을 절대 줄 수 없다 |
| 구현 | 정적 문자열 생성 + Blob 다운로드. 서버 불필요 |
| 부수 효과 | 신청 전 단계에서 **일정을 선점**하게 만든다 — 전환에 직접 기여 |

**대안 B — 월 타임라인 스트립 (P2)**

| 항목 | 내용 |
| --- | --- |
| 형태 | 가로축 = 날짜, 개강 구간만 막대. 빈 날짜는 눈금으로만 |
| 장점 | 2일 과정이 막대로 **자연스럽게** 표현된다(캘린더의 span 문제 소멸). 빈 공간이 격자가 아니라 여백이라 시각적 부담이 없다 |
| 반응형 | 모바일에서는 **세로 타임라인**으로 회전 — 리스트와 형태가 수렴하므로 별도 구현 가치가 떨어진다 |
| 기존 자산 | `UpcomingSessionsStrip` 컴포넌트가 이미 있다. 확장 여지 있음 |
| 판단 | 데스크톱 전용 부가 뷰로는 매력적이나, **신규 정보를 주지 않는다.** 배포 일정 안에서는 순위가 낮다 |

### 5-5. 결론

> **월간 그리드 캘린더는 만들지 않는다.** 대신 **「캘린더에 추가」(ICS)**를 넣는다.
> 사용자가 원한 것은 캘린더 화면이 아니라 **자기 일정과의 대조**였다.
